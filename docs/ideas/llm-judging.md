# LLM 判定工程（構想）

Issue #48・#2。**未実装**（`scripts/llm/` は存在しない）。決定論の収集の後段に、紹介文・スパム一次判定・分類候補を LLM で作る工程を置く設計案。方針は [discovery-policy.md](../collection/discovery-policy.md)、運用ルールは [operations/jobs.md](../operations/jobs.md#鍵クレジットllm-予算)。

## 設計案

- **手元のスクリプトから Claude API で実行**する。公開サーバーからは呼ばない。Claude Code の対話トークンは使わない。
- 入力は決定論スクリプトが取得した文章のみ（title、meta description、本文抜粋、lang、広告タグ比率などの特徴量）。LLM は Web に出ない。
- 出力は JSON スキーマ固定: `description_ja` / `description_en`（同じ事実のみ・原文に無いことを足さない）、スパム判定（pass / suspect / reject ＋理由）、広告・企業・パーキング・成人系の別、カテゴリ候補（既存の木の id）、タグ、信頼度、国・区画の根拠が本文にあれば引用つき。
- 全件「候補」として台帳に保存し、公開は承認後。判定ごとに入力ハッシュで結果をキャッシュする。
- バッチ実行（Message Batches API）とプロンプトキャッシュ、ドライラン（API を呼ばず見積り）を持つ。
- 予算ガード: 実行ごとの上限、全体の上限（予備を残す）、1 件ごとの usage から費用を記録（入力・出力・キャッシュのトークンと推定費用）、超過で停止、残額は Console の残高と突き合わせる。
- モデルは軽量モデルを既定にし、迷う/信頼度が低いものは上位モデルで再判定する案。月額クレジットは期限で失効するため、費用より品質を優先してよい（2026-11-13 の方針）。
- スパム判定は 2 段階: ①決定論の粗い信号（広告タグの多さ、本文の薄さ、量産ドメイン等）で明らかなものを除外/要注意に、②LLM が残りを「通す/怪しい/落とす」＋理由で一次判定。「落とす」は確信が高いものだけ自動リジェクト（理由と時刻を記録、復活可能）。「怪しい」は人間レビュー。判定精度は人間が見た件で検証して閾値を調整する。AI 使用そのものは減点しない。

## 第 1 段の計画（Issue #48）

単独プロトタイプとして、既掲載サイトを入力に実行し、人が書いた紹介文・カテゴリと比べて品質（事実の足し過ぎ・誤訳・カテゴリの妥当性）を評価し、1 件あたりの費用・所要時間・モデル別の差を実測して Issue に記録する。その後、パイプラインの候補台帳に接続する口を用意する。
